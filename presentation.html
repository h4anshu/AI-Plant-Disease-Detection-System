From Leaf to Loss  ·  AI Plant Disease Detection System

Introduction
01 — Introduction

A farmer photographs a leaf. The system returns a diagnosis, a severity, and a cost.

Six Indian field crops, thirty-two disease classes. The user picks the crop and uploads one photo; a CNN identifies the disease, image statistics grade how far it has progressed, and a literature-backed table converts that into an estimated yield loss — the number a farmer actually acts on.

02 — Aims & Objectives

Close the gap between “what disease is this?” and “what will it cost me?”

Most leaf-disease demos stop at a class label. The objectives below are the pipeline in order — each stage exists because the next one needs its output.

  1. 01
    Diagnose the disease

    Classify a leaf photo into the correct disease for a user-selected crop, across 3–11 classes depending on the crop.

  2. 02
    Grade the severity

    Estimate affected leaf area per image and bin it as early, moderate, or severe — computed live from the photo, not looked up.

  3. 03
    Show the model’s reasoning

    Return a Grad-CAM heatmap with every prediction, so a confidence score is never the only evidence a user has.

  4. 04
    Translate into treatment and cost

    Map (crop, disease) to advisory text and (crop, disease, severity) to a yield-loss percentage drawn from published agronomy literature.

  5. 05
    Stay extensible and honest

    Add a seventh crop by training one head, not the whole model — and tag every estimate with the confidence its source data actually supports.

04 — Potential Challenges & Risks

One class scored 100%. That was the problem.

Dataset shortcuts found & fixed

Wheat’s Yellow_Rust class came from a separate dataset with distinctive dark macro photography. Grad-CAM showed the head recognising the folder, not the fungus. The class was removed and wheat retrained as 5-class.

Lab photography bias open risk

Training data is mostly staged: uniform backgrounds, controlled lighting. Performance on a farmer’s phone camera in a cluttered field is unverified.

Severity is a heuristic, not a measurement 44% agreement

Validated against expert grades from Yellow-Rust-19. Four methods were built; the best reproducible one agrees 44% of the time. Directionally useful, not clinical.

Small-dataset crops pigeonpea 79%

973 raw images against wheat’s 16,000. Accuracy tracks dataset size almost exactly, and no augmentation is applied during head training.

Yield loss is a lookup table scope decision

No soil, weather, sowing date, or variety input. Two farmers with the same diagnosis get the same percentage — stated as a constraint rather than hidden.

05 — Feasibility & Viability

Built, trained, and deployed — the architecture is what makes it cheap to keep going.

Held-out test sets · pigeonpea marked as the known weak point

Training cost

The backbone runs over each image once and its 1280-dim features are cached to disk. Heads then train on those vectors in seconds per crop instead of about an hour — and a frozen backbone can’t be corrupted by whichever crop trained last.

Adding a crop

Mustard is deferred, not blocked: adding it means training one new head and dropping it in, with nothing else retrained. Chickpea was dropped outright because no available source has a healthy-leaf class.

Running today

FastAPI and Express are containerised on Google Cloud Run (asia-south1), React on Vercel, with MongoDB Atlas and Cloudinary as managed services. All six heads load once at startup, not per request.

Why it holds up in use

The farmer selects the crop, matching how production agri apps work — removing one compounding error source. Every yield figure carries a high / med / low confidence tag traceable to its source.
